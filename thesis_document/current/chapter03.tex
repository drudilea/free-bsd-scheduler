\chapter{Desarrollo}

\section{Introducción}
En este capítulo, se detalla el desarrollo de las mejoras implementadas en el planificador a corto plazo basado en Redes de Petri para el sistema operativo FreeBSD. El trabajo realizado se fundamenta en la colaboración y continuidad de proyectos previos desarrollados por estudiantes de la institución.\par

La comprensión y depuración del código existente, así como la adaptación de los archivos del código fuente de FreeBSD relacionados con el planificador 4BSD, fueron tareas esenciales en el proceso de desarrollo. Este esfuerzo intenta reflejar buenas prácticas en ingeniería de software, una prioridad durante las primeras etapas de desarrollo. El enfoque adoptado integró principios de trabajo en equipo y metodologías ágiles, permitiendo una iteración continua y mejorada sobre el código. A lo largo del desarrollo, se implementaron prácticas de gestión de versiones y estrategias de ramificación para garantizar la calidad y estabilidad del código en cada una de sus etapas. En las siguientes secciones, se detallan las metodologías utilizadas y los módulos específicos desarrollados, subrayando la importancia de cada componente en el contexto del planificador 4BSD.\par


\section{Metodologías de trabajo}
Para abordar el desarrollo de este proyecto de manera efectiva, se estableció una serie de metodologías de trabajo orientadas a mantener una organización rigurosa y una documentación detallada en cada etapa del proceso. El objetivo no fue solo avanzar de manera sistemática, sino también crear un recurso valioso para futuros trabajos en este ámbito.\par

La primera etapa consistió en una profunda revisión del informe del trabajo integrador previo, así como del código base de los archivos de interés en el planificador 4BSD. Este proceso se realizó de forma iterativa, con el propósito de comprender y extender la documentación de ambos componentes antes de proceder. Ampliar la documentación en esta etapa de análisis inicial fue crucial para establecer una base sólida sobre la cual construir el resto del proyecto.\par

Una vez completada la fase de comprensión y documentación, se definieron metodologías de trabajo enfocadas en estrategias que facilitaran la colaboración y la gestión del proyecto. Se implementó una estrategia de ramas estandarizada en el repositorio derivado (\textit{fork}) de FreeBSD, permitiendo un control preciso de las versiones y facilitando la integración continua. Además, se creó un repositorio externo dedicado a almacenar toda la documentación y los recursos necesarios para el desarrollo, garantizando un acceso fácil y organizado a la información relevante.\par

Estas metodologías permitieron trabajar de manera ordenada y eficiente, y también sentaron las bases para una colaboración efectiva y una fácil transición del conocimiento. En las siguientes secciones, se detallan las estrategias específicas utilizadas.\par

\subsection{Estrategia de ramificación}
Definir una estrategia de ramificación o \textit{branch strategy} en los proyectos es fundamental para mantener el control sobre el flujo de trabajo, la organización del proyecto y asegurar que las modificaciones se integren sin problemas en la rama principal del código. Una estrategia bien definida establece un conjunto de reglas claras y consistentes para la creación y fusión de ramas de código.\par

Además, esta estrategia facilita el mantenimiento de un historial completo y bien organizado de las modificaciones realizadas al código, lo cual es esencial para el seguimiento y la continuidad del proyecto. En este caso, se definió el prefijo de branches utilizando los apellidos de los integrantes del grupo de trabajo, como por ejemplo, \texttt{\textbf{DrudiGoldmanPI/}}. Este enfoque ayuda a identificar y localizar fácilmente todos los cambios realizados en este proyecto integrador.\par

Para definir los nombres de las ramas, se establecieron tres casos principales por los cuales se crearían nuevas ramas:

\begin{itemize}
    \item \textbf{Pruebas}: Ramas creadas para realizar pruebas y verificar que ciertas partes del código fuente funcionen según lo esperado. Este tipo de ramas se utilizan principalmente para la depuración mediante el uso de registros.
    \item \textbf{Update}: Ramas dedicadas a la actualización del código base con las versiones más recientes de FreeBSD. Esto es especialmente relevante en la fase inicial del proyecto, cuando se deben integrar los cambios previos realizados en el proyecto integrador anterior.
    \item \textbf{Feature}: Ramas utilizadas para el desarrollo de nuevas funcionalidades o la adición de código no existente previamente. Estas ramas permiten la implementación y prueba de nuevas características sin afectar la estabilidad de la rama principal.
\end{itemize}

Con estos tres casos principales (o causas), se definió la estrategia de nombrado de ramas de la siguiente forma:

\begin{center}
    \texttt{\textbf{DrudiGoldmanPI/<CAUSA>\_<DESCRIPCIÓN>-<VERSION\_FREEBSD>}}
\end{center}

Donde \texttt{\textbf{<DESCRIPCIÓN>}} es una breve explicación del contenido de los cambios y \texttt{\textbf{<VERSION\_FREEBSD>}}, es la versión de FreeBSD que se utilizó para realizar los cambios.

Por ejemplo, \textit{DrudiGoldmanPI/feature\_cpuMonopolized-13.1.0} es una rama destinada a la implementación del módulo de monopolización, el cual se detalla más adelante en esta sección de desarrollo; mientras que \textit{DrudiGoldmanPI/update\_petriNetScheduler-12.3.0} corresponde a una rama utilizada para la actualización del planificador 4BSD, modelado mediante Redes de Petri, a la versión 12.3.0 del sistema operativo.\par

\subsection{Conventional Commits}
En este proyecto, se utilizó la convención de \textit{Conventional Commits} para mantener un historial de cambios claro y consistente. Esta práctica facilita la lectura y comprensión de los cambios realizados, tanto para el equipo de desarrollo como para futuros colaboradores.\par

Los mensajes de \textit{commit} siguen un formato estandarizado que describe de manera concisa el tipo de cambio, la versión del sistema operativo afectada y una breve descripción de la modificación. A continuación, se presentan algunos ejemplos extraídos del proyecto:

\begin{itemize}
    \item \texttt{feat(13.1.0): Move thread lock before resource\_expulse\_thread()}
    \item \texttt{fix(13.1.0): Fix sched\_pickcpu for cases when resource\_choose\_cpu returns -1 (NOCPU)}
    \item \texttt{refactor(13.1.0): Change kernel config file identifier}
    \item \texttt{feat(12.3.0): Short term scheduler modeling with PN - Add PI code to release/12.3.0}
\end{itemize}

Los tipos de cambios más comunes utilizados incluyen:
\begin{itemize}
    \item \textbf{feat}: Para la adición de nuevas funcionalidades.
    \item \textbf{fix}: Para la corrección de errores.
    \item \textbf{refactor}: Para modificaciones que mejoran el código sin alterar su funcionalidad.
\end{itemize}

Para la integración de cambios, se adoptó la estrategia de \textit{squash merge}. Esta técnica permite consolidar todos los cambios de una rama en un único \textit{commit} bien detallado, lo cual simplifica el historial del proyecto y facilita el seguimiento de avances importantes. Cada \textit{squash merge} incluye un resumen comprensivo de todos los \textit{sub-commits} que forman parte del cambio, garantizando así una documentación clara y precisa del progreso del proyecto.\par

\subsection{Consulta a la comunidad de FreeBSD}

Durante la depuración de un \textit{kernel panic} asociado a fallos de página bajo carga, se abrió una consulta pública en los foros de FreeBSD\cite{bib6}. El objetivo fue pedir orientación sobre estrategias de depuración, ya que el fallo aparecía de forma aleatoria, se observaba con mayor frecuencia bajo carga elevada y el \textit{kernel} genérico no presentaba el mismo comportamiento en las pruebas realizadas.\par

En esa consulta se compartió información del entorno de trabajo, incluyendo la versión FreeBSD 13.1, el uso del planificador 4BSD, las opciones de depuración activadas, salidas de \texttt{kgdb} y fragmentos del \textit{backtrace} donde el fallo aparecía en caminos alejados del planificador. Las respuestas recibidas sugirieron revisar la correspondencia entre símbolos de depuración y \textit{kernel}, comparar contra un \textit{kernel} 4BSD sin modificaciones, revisar registros y direcciones alrededor del punto de fallo, considerar la desactivación de optimizaciones para depurar y avanzar hacia depuración en vivo cuando fuera posible.\par

Esta interacción no constituyó una contribución técnica al proyecto FreeBSD ni un reporte formal de error aceptado por el proyecto. Su aporte dentro de este trabajo fue más limitado y concreto: brindó criterios de depuración y ayudó a orientar el análisis hacia la posibilidad de que el fallo observable fuera consecuencia de una corrupción o desincronización introducida por las modificaciones del planificador. Ese análisis fue luego desarrollado con mayor profundidad mediante \texttt{kgdb} e instrumentación con \textit{DTrace}, como se describe en la sección \ref{ch:problema_red}.\par

\section{Módulo de actualizaciones}

El desarrollo del proyecto se organizó en módulos, cada uno con objetivos específicos y alcanzables para asegurar avances concretos en cada etapa.\par

En la fase inicial, el trabajo se enfocó en una tarea esencial en cualquier proyecto de software: mantener la compatibilidad con versiones más recientes del sistema operativo. De esta forma, se obtuvieron beneficios significativos en términos de estabilidad y compatibilidad, resultando en un sistema más confiable y mejor posicionado para futuras actualizaciones.\par

El trabajo comenzó con la versión 11 de FreeBSD, basado en el trabajo integrador previo realizado por Nicolás Papp y Tomás Turina, y se extendió hasta FreeBSD 13.1, versión definida como objetivo de migración para este proyecto.\par

Para gestionar las actualizaciones de manera ordenada y efectiva, así como también, comprender mejor los cambios entre versiones; el módulo se dividió en tres etapas progresivas: actualización a la última \textit{release} de la versión 11, y actualizaciones a las versiones 12 y 13 de FreeBSD.\par


\subsection{Actualización a la última \textit{release} de la versión 11}

En esta primera iteración se buscó llevar los cambios del proyecto integrador previo realizados en la versión 11.0.0 del sistema operativo FreeBSD a la última \textit{release} de esta versión, es decir, al 11.4.0.\par

Durante dicha actualización, se identificó un cambio significativo que tuvo un impacto relevante en este proyecto: la modificación en la función \verb|maybe_preempt()|. En la versión anterior, esta función se encargaba de determinar si un nuevo hilo debía tomar el control del procesador inmediatamente, reemplazando al hilo actual en ejecución. En caso afirmativo, se realizaba el cambio de contexto y comenzaba su ejecución, sustituyendo al hilo que se encontraba en el procesador.\par

En la versión más reciente, se introdujo una nueva estrategia, posponer el cambio de contexto para un momento más adecuado mediante un sistema de banderas. En lugar de realizar el cambio de contexto de manera inmediata, se implementó un mecanismo donde el hilo recién encolado establece el valor de la bandera \verb|td_owepreempt| en 1, indicando la necesidad de desalojar al que se encuentra en ejecución, para así tomar el control.\par

Si bien el método de \textit{preemption} no se encuentra modelado en la Red de Petri de recursos, este cambio impactó en el código del planificador desarrollado, ya que implicó la remoción de algunos disparos de transiciones que se provocaban en el cambio de contexto inmediato. Con la nueva estrategia, fue necesario ajustar el código de la Red de Petri para reflejar el cambio en la política de planificación.\par

\subsection{Actualización a la versión 12}

Al comparar las diferencias entre las versiones 11.4.0 y 12.3.0 (última \textit{release}) de FreeBSD, no se encontraron cambios relevantes en los archivos directamente intervenidos por el planificador desarrollado. La revisión se concentró en \verb|sched_4bsd.c|, \verb|kern_thread.c| y en los puntos donde el modelo de Petri se vincula con el encolado, la selección de CPU y el cambio de contexto.\par

Esta etapa se mantuvo como un punto de control dentro de la migración. Aunque no requirió cambios específicos en el código del planificador, permitió separar dos situaciones distintas: por un lado, una actualización de versión que no alteraba los puntos de integración del modelo; por otro, los cambios de FreeBSD 13 que sí modificaban el flujo de \verb|sched_switch()| y requerían adaptar la implementación. De esta forma, los problemas encontrados en la versión 13 no quedaron mezclados con diferencias arrastradas desde la rama 12.\par


\subsection{Actualización a la versión 13}

La versión 13 trajo con ella varios cambios significativos en el código del planificador. Los cambios principales, y que mayor tiempo de análisis e investigación tomaron, fueron los cambios dentro de la función \verb|sched_switch()|, función encargada de realizar el cambio de contexto entre hilos en el planificador 4BSD.\par

El primero de ellos (ver Apéndice \ref{appendix:apA1}) ya se encuentra en la firma de la función y sus variables: previamente, \verb|newtd| era un parámetro de \verb|sched_switch()| que se utilizaba para indicar explícitamente el hilo que se iba a ejecutar a continuación. Sin embargo, en la versión 13, el parámetro \verb|newtd| se eliminó y con ello se simplificó la lógica de selección del hilo (ver Apéndice \ref{appendix:apA3}), teniendo que ajustar algunos disparos en la Red de Petri que previamente eran necesarios para mantener la coherencia de los recursos relacionados, con estos desencolados en el planificador.\par

En la versión 13 de FreeBSD, se realizó una reorganización significativa de los bloqueos en la función \verb|sched_switch()| (ver Apéndice \ref{appendix:apA2}). Estos cambios introdujeron comportamientos inesperados en la red, como el disparo de transiciones no sensibilizadas que desajustaban el estado de la red y causaban fallos en el sistema. Después de depurar el código, se identificó que el problema principal era el manejo incorrecto de la transición \verb|RETURN_VOL|. Específicamente, el método \verb|resource_expulse_thread()| estaba disparando esta transición sin bloquear previamente el \verb|td_lock|. Sin este bloqueo, no era posible cambiar el estado del hilo, lo que impedía que regresara al estado de \verb|CAN_RUN| o listo para ejecutarse. Como resultado, ningún hilo podía ser ejecutado por los procesadores más de una vez, lo que bloqueaba el sistema. Tras realizar los ajustes necesarios, se resolvió este problema y se garantizó el correcto funcionamiento de la red.\par

\subsection{Resultados}

Durante la actualización a las diferentes versiones del sistema operativo FreeBSD, se logró garantizar el funcionamiento correcto de todas las versiones. Esto permitió no solo mantener el proyecto al día, sino también profundizar en el código del sistema operativo y comprender su funcionamiento de manera más integral.\par

La lectura y el análisis del código fuente en profundidad permitieron adquirir un conocimiento detallado del proyecto y de su estructura y características particulares. Esta inmersión en el código brindó una base sólida para abordar tareas posteriores de manera más eficiente y efectiva.\par

Adicionalmente, durante el proceso de actualizaciones, se identificaron, realizaron y documentaron algunas mejoras respecto a versiones anteriores del proyecto. Dichas mejoras fueron registradas en el repositorio de documentación (apartado \ref{sect:wiki}); y algunas de ellas, en el presente documento, con el objetivo de mantener un registro detallado y accesible para trabajos futuros.\par

\subsection{Próximos pasos}

Como se desarrolló previamente, se sostiene la importancia de mantener el proyecto actualizado con las últimas versiones del sistema operativo FreeBSD para asegurar su eficiencia, seguridad y compatibilidad con tecnologías más recientes.\par

Para lograr este objetivo, es esencial monitorear continuamente las actualizaciones y aplicar los cambios necesarios de manera oportuna. Esto evitará el rezago respecto a \textit{releases} más recientes y garantizará que el proyecto se beneficie de las últimas mejoras y correcciones de errores.\par

Mantener el software actualizado en proyectos de código abierto como FreeBSD no solo mejora el rendimiento y la seguridad, sino que también facilita una integración más estrecha con la comunidad de desarrolladores y usuarios. Estar al día con las actualizaciones permite recibir retroalimentación valiosa, contribuyendo al desarrollo colaborativo.\par

Para futuros trabajos en este proyecto, se recomienda priorizar la importancia de este aspecto y comprometerse a dedicar los recursos y el tiempo necesarios para llevar a cabo las actualizaciones de manera regular.\par

\section{Consideraciones comunes de diseño para los módulos desarrollados}

Los módulos desarrollados en este trabajo modifican la forma en que el planificador decide qué procesadores pueden recibir nuevos hilos. Aunque cada módulo tiene un objetivo distinto, ambos comparten algunas restricciones de diseño relacionadas con el funcionamiento interno de FreeBSD.\par

\subsection{Tratamiento del procesador 0}\label{sect:cpu0-modulos}

Tanto el módulo de inhibición de asignación de trabajo como el módulo de monopolización excluyen al procesador 0 de las operaciones configurables por el usuario. Esta decisión se tomó como una medida conservadora para preservar la estabilidad del sistema durante las pruebas realizadas.\par

La CPU0 suele tener un rol particular en distintas rutas internas del \textit{kernel}. Como se explicó al describir las restricciones de afinidad y \textit{bounding} del planificador 4BSD, existen casos donde FreeBSD vincula explícitamente la ejecución a este procesador, por ejemplo en caminos asociados a \verb|kern_reboot()|. Además, dependiendo de la plataforma y de la configuración del sistema, pueden existir interrupciones o tareas internas con afinidad hacia CPU0. Por ese motivo, inhibir o monopolizar este procesador no es equivalente a hacerlo sobre cualquier otro núcleo disponible.\par

Durante el desarrollo se observó que aplicar estos módulos sobre CPU0 podía producir comportamientos inestables. En lugar de incorporar una excepción parcial sin comprender completamente todos los caminos internos involucrados, se decidió impedir su selección dentro de ambos módulos. Esta restricción no implica que sea imposible diseñar una política que incluya CPU0, sino que dicha posibilidad requiere un análisis específico de afinidad, interrupciones y caminos obligatorios del \textit{kernel} que quedó fuera del alcance de este prototipo.\par

La limitación tiene un costo práctico: en sistemas con pocos núcleos, excluir CPU0 reduce de forma directa la cantidad de procesadores que pueden ser inhibidos o monopolizados. Por lo tanto, la decisión mejora la estabilidad del prototipo, pero también restringe su aplicabilidad en equipos de baja cantidad de CPUs.\par

\subsection{Relación con mecanismos nativos de afinidad de FreeBSD}

FreeBSD ya ofrece mecanismos para limitar o fijar la ejecución de hilos y procesos a ciertos procesadores. Herramientas como \verb|cpuset| y llamadas como \verb|cpuset_setaffinity()| permiten definir conjuntos de CPUs permitidas, mientras que mecanismos internos como \verb|sched_bind()|, los hilos \textit{pinned} y los hilos \textit{bound} expresan restricciones más fuertes dentro del \textit{kernel}. Por lo tanto, los módulos desarrollados en esta tesis no deben entenderse como un reemplazo general de esas funcionalidades.\par

La diferencia principal está en el lugar donde se representa la restricción. Los mecanismos nativos indican dónde puede correr un hilo o un proceso. En cambio, los módulos desarrollados incorporan parte de esa decisión al modelo de recursos del planificador basado en Redes de Petri. La pregunta deja de ser únicamente qué CPUs tiene permitidas un hilo y pasa a incluir qué CPUs están disponibles, dentro del marcado de la red, para recibir nuevo trabajo ordinario.\par

En el módulo de inhibición, esta diferencia aparece con claridad. Un uso de \verb|cpuset| puede limitar la ejecución de un proceso o conjunto de procesos a ciertas CPUs. El módulo desarrollado, en cambio, representa la disponibilidad de cada CPU como parte de la red de recursos: cuando una CPU queda inhibida, el modelo impide que la política normal del planificador la elija para nuevos encolados ordinarios. El procesador no se apaga ni se retira del sistema; simplemente deja de participar en esa decisión de asignación.\par

En el módulo de monopolización, FreeBSD ya cuenta con mecanismos para fijar hilos a CPUs concretas. El aporte del módulo no consiste solamente en ubicar un hilo en una CPU, sino en impedir que esa CPU reciba hilos ordinarios distintos del hilo seleccionado mientras la reserva permanece activa. Para lograrlo, se agregó una estructura auxiliar consultada durante la selección de CPU. Esta decisión no quedó completamente expresada como una extensión de la red, pero sí se integró al punto donde el planificador decide si una CPU puede aceptar o no un hilo determinado.\par

De esta forma, el aporte de los módulos no es ofrecer una API de afinidad más completa que las existentes en FreeBSD. Su aporte es estudiar cómo esas restricciones pueden convivir con un planificador modelado mediante Redes de Petri, qué parte puede expresarse directamente con plazas y transiciones, y en qué casos hace falta lógica auxiliar para conservar la coherencia con las reglas internas del \textit{kernel}.\par

\section{Módulo de inhibición de asignación de trabajo a procesadores}

Tras completar las actualizaciones del sistema operativo, el siguiente paso fue desarrollar una nueva funcionalidad para controlar, desde el planificador, qué núcleos pueden recibir nuevos hilos. Esta funcionalidad permite inhibir manualmente la asignación de trabajo a determinados núcleos, sin apagar físicamente el procesador ni intervenir sobre la administración energética del hardware.\par

Este módulo es útil como punto de partida para estudiar escenarios donde la carga de trabajo cambia con el tiempo, ya que permite decidir qué núcleos participan en la selección de colas y cuáles quedan excluidos. Aunque aún no se implementó una estrategia automática ni se midió ahorro energético, el mecanismo podría combinarse en trabajos futuros con políticas de carga, prioridad o administración de energía.\par

\subsection{Objetivos}

El objetivo general de esta sección fue desarrollar una funcionalidad dentro del planificador de FreeBSD que permita habilitar o deshabilitar manualmente la asignación de trabajo a diferentes núcleos del procesador.\par

Esta funcionalidad permite explorar escenarios con distinta cantidad de procesadores disponibles, restringir núcleos para ciertas políticas de planificación y modificar ese estado durante la ejecución del sistema.\par

\subsection{Primera Iteración: Implementación del Módulo de Inhibición mediante cambios en la Red de Petri}

Para iniciar la implementación del módulo de inhibición de asignación de trabajo a núcleos del procesador, se debatieron dos enfoques relacionados con la Red de Petri del sistema operativo. El primero proponía utilizar las plazas y transiciones ya existentes, agregando políticas nuevas en el código del planificador. El segundo, que fue el adoptado, consistía en sumar plazas y transiciones a la Red de Petri para representar si un núcleo puede recibir nuevos hilos. Se optó por esta alternativa porque integraba el módulo al modelo existente sin cambiar de forma drástica la estructura del planificador. Además, permitía habilitar o inhibir la asignación de trabajo a un núcleo desde distintas partes del sistema mediante el disparo de una transición.\par

Con esta decisión en mente, el primer paso fue crear un indicador que permitiera conocer si cada procesador se encuentra habilitado o inhibido para recibir nuevos hilos. Para esto, se añadió una nueva plaza en la Red de Petri, llamada \verb|PLACE_SUSPENDED|. La presencia o ausencia de un \textit{token} en esta plaza indica si un procesador está disponible para encolar y ejecutar hilos ordinarios.\par

La plaza \verb|PLACE_SUSPENDED| está acompañada de dos transiciones que manejan el \textit{token} correspondiente: \verb|TRAN_SUSPEND_PROC| para deshabilitar el núcleo, y \verb|TRAN_WAKEUP_PROC| para habilitarlo nuevamente. Se añadió un arco inhibidor a la transición que libera el recurso para asegurar que la plaza funcione como un recurso único. Una vez que un procesador está deshabilitado, solo la transición que lo habilita de nuevo queda sensibilizada.\par

En resumen, la plaza \verb|PLACE_SUSPENDED| controla las transiciones de encolado, tanto de la cola específica de la CPU, como de la cola global. Cuando la CPU está suspendida, impide que nuevos hilos se añadan a su cola y se ejecuten. Sin embargo, es importante destacar que este desarrollo no elimina los hilos que ya estaban en la cola de la CPU antes de que se deshabilitara. Es decir, los hilos ya encolados seguirán siendo ejecutados, pero no podrán volver a la cola de la CPU inhabilitada. Esta lógica está reflejada en la Red de Petri, donde la nueva plaza de suspensión solo afecta a las transiciones de encolado y desencolado, sin interferir en la ejecución de hilos ni en la transición específica de desencolado del procesador (\verb|TRAN_UNQUEUE|).\par

Como primer paso para implementar esta funcionalidad a nivel de código, el trabajo se centró en ajustar las matrices fundamentales que soportan el funcionamiento de la Red de Petri: la matriz base y la matriz de incidencia. Estas matrices son cruciales para la representación y el manejo de las transiciones y plazas en la Red de Petri.\par

La matriz base, que define la estructura inicial de la Red de Petri, necesitaba ser actualizada para reflejar las nuevas plazas y transiciones introducidas. En este informe se usa el nombre matriz base para referirse a la matriz de incidencia local de una CPU: cada celda indica el cambio de marcado producido sobre una plaza cuando se dispara una transición. Es decir, corresponde a la matriz \(C = W^{+} - W^{-}\) de la subred local del recurso.\par

También fue necesario actualizar la matriz de inhibición. A diferencia de la matriz base, esta matriz no representa suma o resta de tokens, sino la presencia de arcos inhibidores: una celda con valor 1 indica que la plaza de esa fila inhibe la transición de esa columna cuando contiene tokens. Una celda con valor 0 indica ausencia de arco inhibidor.\par

En la primera iteración se agregaron entradas para la nueva plaza \verb|PLACE_SUSPENDED| y para las transiciones \verb|TRAN_SUSPEND_PROC| y \verb|TRAN_WAKEUP_PROC|. En la matriz base, esas entradas registran el cambio de marcado asociado a suspender o rehabilitar un procesador. En la matriz de inhibición, registran que un procesador suspendido no debe aceptar ciertos caminos de encolado hasta que vuelva a habilitarse.\par

Como parte de los ajustes realizados en las matrices, se incorporó una nueva función, \linebreak\verb|toggle_active_cpu()|, al archivo de métodos auxiliares de la Red de Petri. Esta función puede ser invocada desde un módulo del \textit{kernel} y está diseñada para alternar el estado de una CPU especificada como parámetro. La función verifica si la transición asociada está sensibilizada y, si es así, procede a dispararla. En resumen, esta adición permite seleccionar y alternar el estado de un procesador, que puede ser suspendido o activado según sea necesario, y se gestiona de manera externa al flujo principal del \textit{kernel}, permitiendo así un control en ejecución del estado de habilitación de la CPU.\par

Tras la implementación de esta funcionalidad, apareció un problema inesperado: la funcionalidad no se comportaba como se había previsto. Específicamente, se recibieron alertas indicando que algunas transiciones no estaban sensibilizadas durante los intentos de disparo. El proceso de depuración reveló que el problema estaba relacionado con el comportamiento del planificador cuando no había hilos disponibles para ejecutar, ni en la cola local del procesador ni en la cola global.\par

En la siguiente sección, se describe la solución implementada para superar esta dificultad.\par

\subsection{Segunda Iteración: Soporte del \texttt{idlethread} en la Red de Petri}
\label{ch:idlethread}

Durante la depuración realizada en la iteración anterior, se identificó un error en situaciones donde una CPU no tenía hilos listos para ejecutar. Para abordar este problema en la segunda iteración del módulo de inhibición, es importante entender el papel del \texttt{idlethread}. En estos casos, el planificador encola y ejecuta el \texttt{idlethread}, una funcionalidad que ya estaba presente antes del inicio del proyecto integrador y que es característica del planificador 4.4BSD utilizado en FreeBSD.\par

El \texttt{idlethread} es un hilo sin carga de trabajo ordinaria para el procesador. Puede ser encolado, suspendido y ejecutado de manera similar a otros hilos. Cada núcleo de CPU tiene asociado su propio \texttt{idlethread}, el cual ejecuta un bucle simple que generalmente consiste en poner la CPU en un estado de bajo consumo.\par

Cuando no hay hilos o procesos listos para ejecutarse en una CPU, el planificador selecciona el \texttt{idlethread} como el siguiente hilo. Dado que el \texttt{idlethread} tiene la prioridad más baja, solo se programa cuando no hay tareas de mayor prioridad disponibles. En cualquier momento en que aparezca un hilo de mayor prioridad, el \texttt{idlethread} será reemplazado por este nuevo hilo.\par

En el trabajo integrador previo, el momento de la toma de decisión del encolado del \texttt{idlethread} no estaba modelado en su totalidad, sino que se simulaban los disparos de transiciones utilizando la cola global, para mantener coherentes los estados en ambas redes (de recursos y de hilos). Es decir, en momentos de inactividad de la CPU, se disparaban las transiciones de \verb|TRAN_QUEUE_GLOBAL| y \verb|TRAN_FROM_GLOBAL_CPU| para encolar, desencolar y ejecutar el \texttt{idlethread}.\par

El problema con este enfoque en el proyecto actual es que la decisión de inhabilitar el procesador mediante el modulo desarrollado bloquea tanto el encolado como el desencolado, ya sea de la cola particular del procesador como de la cola global, lo que hace que el mecanismo utilizado en el proyecto integrador previo quede inutilizable, ya que se intentarán disparar transiciones no sensibilizadas. Por tanto, fue necesario ajustar el modelo de la red de Petri para incluir ahora el comportamiento específico del planificador en los momentos en que se tiene que hacer uso del \texttt{idlethread}.\par

La solución, detallada en la Figura \ref{fig:cpu-on-off-2nd-iteration}, consistió en agregar una nueva transición, \verb|TRAN_EXEC_IDLE|, que permite la ejecución del \texttt{idlethread} cuando no hay hilos en la cola del procesador, contemplando así el caso en que la CPU está suspendida. Tras implementar estos cambios, el modelo comenzó a representar con precisión el proceso interno del planificador.\par

Después de realizar estos ajustes, se pudo proceder a incorporar las modificaciones correspondientes en el código del planificador. Dichos cambios incluyeron la implementación de la lógica detallada previamente, donde en casos de inactividad o inhabilitación manual de algún procesador, el flujo de ejecución de la red y, por tanto, de los procesos e hilos dentro de un núcleo, se comportará de manera esperada.\par

Esta integración permitiría ajustar el estado de los procesadores en ejecución, respondiendo a las necesidades reales del sistema en su conjunto, y no solo a través de un módulo del \textit{kernel}.\par

\section{Módulo de monopolización de hilos por parte de los procesadores}

Tras finalizar el módulo de inhibición de asignación de trabajo a procesadores, el desarrollo se enfocó en el módulo de monopolización de hilos por parte de los procesadores. Este módulo introduce la capacidad en el planificador de anclar hilos a una CPU específica, lo que implica que dicho núcleo solo puede encolar y ejecutar los hilos que están asociados a él.\par

\subsection{Objetivos}

El objetivo de este módulo es proporcionar al planificador 4BSD la capacidad de anclar hilos a procesadores específicos en cualquier momento durante la ejecución del sistema operativo. Esto permitirá definir políticas de asignación de recursos más precisas y adaptables a las necesidades del sistema.\par

Es muy importante que este módulo, al igual que el desarrollado previamente, pueda ser cargado y activado en ejecución del sistema operativo, sin necesidad de reiniciarlo. Esta flexibilidad facilitará su integración con funcionalidades del sistema operativo, como la adaptación dinámica a cambios en la carga de trabajo o la asignación de hilos críticos a núcleos específicos para mejorar el rendimiento, entre otras.\par

\subsection{Primera Iteración: Desarrollo del Módulo de Monopolización a través de Políticas en la Red}

Para implementar el módulo de monopolización, se comenzó con una fase de investigación para explorar las posibles estrategias de desarrollo. Inicialmente, se consideró la opción de diseñarlo como un módulo independiente, similar al módulo de inhibición. Sin embargo, se identificó que en última instancia, la decisión del planificador sobre a qué CPU encolar un hilo, estaba estrechamente vinculada a los identificadores de los hilos que se deseaban ejecutar.\par

Este enfoque llevó a entender el problema en términos de políticas para la toma de decisiones a la hora de encolar un hilo. Para implementar estas nuevas políticas, se agregó un mecanismo que permite fijar un hilo a un procesador específico, asegurando que dicho procesador no pueda encolar ni ejecutar otros hilos mientras esté monopolizado.\par

El proceso utiliza un nuevo registro (\verb|pinned_threads_per_cpu|) que rastrea el estado de monopolización de cada uno de los procesadores. Este registro se define como un arreglo de tantos elementos como procesadores en el sistema, que almacenan el identificador del hilo monopolizando dicho procesador (o -1 en caso de encontrarse libre). Así, cuando el planificador debe decidir donde ejecutar el hilo, primero verifica si este se encuentra \textit{anclado} a un procesador específico. Si es así, el hilo se encola en ese procesador para luego ser ejecutado. En caso contrario, el sistema sigue el proceso estándar de asignación a cualquier procesador disponible.\par

\subsection{Resultados}

Los resultados del módulo fueron satisfactorios, demostrando que los hilos pudieron monopolizar los procesadores de manera efectiva.\par

Para verificar este comportamiento, se realizaron pruebas utilizando una herramienta de monitoreo y un programa de estrés. Estas pruebas consistieron en ejecutar diferentes programas diseñados para mantener hilos activos en los distintos núcleos de las CPUs durante un tiempo prolongado. Inicialmente, se observó el comportamiento global del sistema sin activar el módulo de monopolización. Luego, se seleccionó uno de estos hilos y se lo ancló a un procesador específico. Esto permitió comprobar que el módulo funcionaba correctamente, manteniendo los hilos anclados en un mismo núcleo sin que este pudiera ejecutar otras tareas, lo que confirma la efectividad de la monopolización.\par

Como se indicó en la sección \ref{sect:cpu0-modulos}, el módulo no incluyó la monopolización de CPU0. La decisión se mantuvo por el mismo criterio adoptado en el módulo de inhibición: evitar que el prototipo interfiera con rutas internas del sistema que pueden depender de ese procesador.\par

Los detalles específicos y un análisis más profundo de los resultados se abordarán en el capítulo de “Análisis de resultados”.\par

\subsection{Próximos pasos}

Aunque la implementación de este módulo no genera mejoras inmediatas en el sistema, su potencial radica en su activación bajo demanda, ya sea por señales específicas o por otras partes del \textit{kernel}. Al igual que en el módulo anterior, su funcionalidad se activa solo cuando es necesario, lo que lo hace útil en escenarios concretos.\par

Este módulo puede ser particularmente beneficioso en situaciones donde se requiere garantizar la ejecución de tareas críticas en ejecución o cuando ciertos hilos necesitan acceso exclusivo y preferente a un procesador. Algunos ejemplos en los que podría ser beneficioso el módulo son en momentos de interrupciones de hardware a procesadores específicos, asegurando que estos hilos tengan acceso prioritario y minimizando la latencia en la respuesta a eventos de hardware. También podría ser útil en la gestión de dispositivos de almacenamiento de alto rendimiento, donde es crucial que los hilos responsables del acceso a disco mantengan un rendimiento constante.\par

Otra mejora significante del módulo, sería la de hacer que el mecanismo de anclaje sea más dinámico y flexible. Actualmente, el módulo permite anclar un solo hilo a un solo procesador, pero una posible extensión de esta funcionalidad podría permitir que un procesador ancle múltiples hilos simultáneamente. Esto permitiría una distribución más equilibrada de las cargas de trabajo.\par

Asimismo, se considera la posibilidad de que, en el futuro, se pueda anclar no solo hilos individuales, sino procesos enteros, asegurando que todos sus hilos se ejecuten exclusivamente en ese procesador.\par

\section{Tareas Extra}

Durante el proceso de desarrollo de los módulos, se fueron trabajando además algunas otras problemáticas encontradas.\par

\subsection{Modelado de restricciones internas del planificador}

Durante el desarrollo de los módulos de inhibición y monopolización de procesadores, surgió un problema crítico relacionado con la interacción entre la red de Petri y algunas reglas internas del planificador de FreeBSD. Inicialmente, el caso más visible era el de los hilos \textit{pinned}, pero el análisis posterior mostró que el problema también involucraba a hilos \textit{bound} y a hilos con restricciones de afinidad.\par

En FreeBSD, estas condiciones no son simples preferencias de balanceo. Un hilo \textit{pinned} debe volver a ejecutarse en el último procesador en el que corrió, un hilo \textit{bound} queda asociado a un procesador específico y la afinidad limita el conjunto de CPUs válidas para ejecutar el hilo. Por lo tanto, cuando el planificador debe encolar uno de estos hilos, no siempre puede elegir libremente cualquier cola del sistema.\par

El conflicto apareció porque la transición \verb|TRAN_ADDTOQUEUE| de la red de recursos estaba inhibida por la plaza \verb|PLACE_CANTQ|. Esta inhibición era útil como política de balanceo, ya que evitaba elegir repetidamente una CPU que ya había recibido trabajo. Sin embargo, al mismo tiempo podía impedir que la red registrara un encolado que FreeBSD debía realizar para respetar sus propias reglas internas.\par

La distinción central fue separar las decisiones de política de las restricciones obligatorias del sistema operativo. La red de Petri puede decidir entre varias CPUs válidas cuando el hilo no tiene restricciones fuertes, o cuando hay más de una CPU permitida y sensibilizada. En cambio, cuando FreeBSD exige una CPU concreta, o cuando la red no encuentra una CPU sensibilizada dentro del conjunto permitido, el modelo no puede bloquear el evento real de encolado sin quedar desincronizado respecto del estado del planificador.\par

Esta distinción define el criterio adoptado para abordar el problema: conservar la política normal de la red cuando existe una CPU válida y sensibilizada, pero registrar por otro camino los encolados que FreeBSD debe realizar obligatoriamente. La sección siguiente describe cómo se implementó y validó esta decisión.\par

\subsection{Fallo de página por desincronización entre FreeBSD y la red de Petri}\label{ch:problema_red}

Durante el desarrollo se identificó un problema recurrente que inicialmente parecía estar relacionado con el uso de la placa de red en la máquina virtual. El síntoma aparecía con mayor frecuencia al habilitar SSH para conectarse al sistema, mientras que al desactivar la placa de red antes del arranque el problema dejaba de reproducirse. Sin embargo, el análisis posterior mostró que la placa de red no era la causa raíz, sino un escenario que aumentaba la probabilidad de ejecutar caminos problemáticos del planificador.\par

El síntoma visible era un \textit{kernel panic} provocado por un \textit{page fault}. En varios \textit{crash dumps}, el fallo aparecía en funciones como \verb|kern_select()| o en caminos de espera del \textit{kernel}. Esto dificultó el diagnóstico porque el punto del \textit{crash} no era el lugar donde se había introducido el error. El sistema llegaba a esas funciones con el estado real del planificador y el marcado de la red de Petri ya desincronizados.\par

Al revisar la implementación del proyecto integrador previo, se observó que la decisión de CPU quedaba delegada al método \verb|resource_choose_cpu()|. En ese modelo, si un hilo con restricciones debía ir a una CPU cuya transición \verb|TRAN_ADDTOQUEUE| estaba inhibida por \verb|PLACE_CANTQ|, el planificador podía enviarlo a la cola global. Esta decisión mantenía la red sincronizada con el evento registrado, pero podía incumplir reglas internas de FreeBSD, ya que la cola global puede ser consumida por cualquier CPU y no vuelve a validar las condiciones de \textit{pinning}, \textit{bounding} o afinidad antes de ejecutar el hilo.\par

En versiones posteriores se intentó respetar mejor esas reglas internas. Para hilos \textit{pinned}, \textit{bound} o con afinidad restringida, el planificador encolaba el hilo en la CPU correspondiente o dentro del conjunto permitido por FreeBSD. El problema era que, si la red tenía esa CPU inhibida por \verb|PLACE_CANTQ|, la transición \verb|TRAN_ADDTOQUEUE| no estaba sensibilizada. En consecuencia, FreeBSD agregaba el hilo a la \textit{run queue} real, pero la red no sumaba el token correspondiente en \verb|PLACE_QUEUE| ni actualizaba correctamente su estado.\par

A partir de ese momento, la red dejaba de representar el estado real del planificador. Cuando FreeBSD luego intentaba sacar ese hilo de la cola para ejecutarlo, la red podía intentar disparar \verb|TRAN_UNQUEUE| sin haber registrado antes el \verb|TRAN_ADDTOQUEUE| correspondiente. Esa misma diferencia de marcado podía propagarse a transiciones posteriores como \verb|TRAN_EXEC|, \verb|TRAN_RETURN_INVOL|, \verb|TRAN_RETURN_VOL| o \verb|TRAN_REMOVE_QUEUE|. Por este motivo, el \textit{kernel panic} terminaba apareciendo más tarde y en otro punto del \textit{kernel}: el error observable era consecuencia de haber desincronizado previamente el estado real de FreeBSD y el marcado de la red.\par

Para llegar a esta conclusión fue necesario combinar varias formas de depuración. En primer lugar se analizaron los \textit{crash dumps} con \texttt{kgdb}, utilizando la pila de llamadas para ubicar el punto observable del fallo y confirmar que el \textit{page fault} aparecía fuera del código del planificador. Luego se revisaron los eventos previos registrados por el \textit{kernel}, especialmente los casos de transiciones no sensibilizadas disparadas desde \verb|sched_add()|. Esa evidencia permitió dejar de tratar el problema como un fallo asociado a la placa de red y reconstruir la secuencia real: una decisión de encolado obligatoria para FreeBSD no quedaba registrada en la red, y el error recién se manifestaba más adelante cuando la red intentaba continuar desde un marcado incorrecto.\par

La solución implementada consistió en separar el encolado decidido por la política de la red del encolado impuesto por restricciones de FreeBSD. La transición original \verb|TRAN_ADDTOQUEUE| se conserva como camino normal de política y sigue estando inhibida por \verb|PLACE_CANTQ|. Para los casos en los que el \textit{kernel} necesita registrar un encolado obligatorio, se agregó una transición \verb|TRAN_ADDTOQUEUE_FORCED|. Esta transición no está inhibida por \verb|PLACE_CANTQ|, por lo que evita la desincronización, pero mantiene la incidencia sobre \verb|PLACE_QUEUE| y \verb|PLACE_CANTQ|. De esta forma, la CPU que recibió un hilo forzado igualmente queda penalizada para futuras decisiones libres de la red.\par

La Figura \ref{fig:addtoqueue-forced-subnet} muestra esta diferencia sobre un recorte de la subred de encolado per-CPU. Para simplificar la explicación, se dejaron únicamente las plazas y transiciones necesarias para entender el nuevo camino forzado y su continuidad dentro de la red de recursos. Por ese motivo se omiten caminos de retorno, remoción, cola global y control SMP, que siguen formando parte de la red completa pero no modifican el punto central del cambio. En el recorte puede verse que ambas transiciones agregan un token a \verb|PLACE_QUEUE| y a \verb|PLACE_CANTQ|. Luego, el token agregado en \verb|PLACE_QUEUE| permite continuar por el camino normal de ejecución, comenzando por \verb|TRAN_UNQUEUE|. La diferencia es que solo el camino de política conserva el arco inhibidor desde \verb|PLACE_CANTQ|.\par

Con este cambio, los hilos \textit{pinned} y \textit{bound} se registran mediante el camino forzado, ya que FreeBSD impone una CPU concreta. Para hilos con afinidad, la red primero intenta elegir una CPU permitida mediante \verb|TRAN_ADDTOQUEUE|. Si no existe una CPU válida y sensibilizada dentro del conjunto permitido, se utiliza \verb|TRAN_ADDTOQUEUE_FORCED| como respaldo para mantener la coherencia entre el estado real del planificador y el marcado de la red.\par

Una vez definida la corrección, se agregó instrumentación específica con \textit{DTrace} para validarla sin depender de impresiones masivas desde el \textit{kernel}. Para esto se incorporó un proveedor \verb|SDT| propio, descripto en el Apéndice \ref{appendix:dtrace-sdt}, con eventos asociados al disparo de transiciones, a intentos bloqueados y a las decisiones tomadas por \verb|sched_add()|. Las trazas permitieron distinguir si un hilo era enviado a la cola global, si era encolado en una cola per-CPU por decisión de la política de Petri, o si era registrado mediante \verb|TRAN_ADDTOQUEUE_FORCED|. Con esta instrumentación se pudo observar el comportamiento del modelo en ejecución real, validar que la transición original seguía siendo utilizada cuando correspondía y verificar que los encolados obligatorios quedaran registrados sin volver a desincronizar la red.\par

\subsection{Análisis formal del modelo extendido}

Además de la validación en ejecución, se revisaron formalmente los modelos de Red de Petri utilizados durante el desarrollo. El alcance de este análisis es acotado: no pretende demostrar propiedades del \textit{kernel} completo, sino comprobar que las extensiones agregadas al modelo conservan relaciones estructurales básicas y no introducen estados de \textit{deadlock} en los escenarios analizados.\par

Para esto se trabajó con dos modelos principales. El primero fue el submodelo reducido de encolado forzado mostrado en la Figura \ref{fig:addtoqueue-forced-subnet}, usado para mirar de forma aislada el cambio introducido por \verb|TRAN_ADDTOQUEUE_FORCED|. El segundo fue un modelo consolidado de una CPU, mostrado en la Figura \ref{fig:resource-final-1cpu}, que reúne la suspensión de procesadores, la ejecución del \texttt{idlethread} y el encolado forzado. De esta manera, el modelo consolidado permite observar en una misma red la inhibición manual de asignación de trabajo y el registro de encolados obligatorios de FreeBSD.\par

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{images/resource-final-1cpu.png}
    \caption[Modelo consolidado de recursos para una CPU]{Modelo consolidado de recursos para una CPU utilizado en el análisis formal. La red integra la inhibición manual de asignación de trabajo, la ejecución del \texttt{idlethread} y la transición de encolado forzado.}
    \label{fig:resource-final-1cpu}
\end{figure}

En los modelos analizados se identificaron algunos invariantes estructurales útiles para revisar la consistencia del marcado. En la red de hilos presentada en la Figura \ref{fig:threadModel}, por ejemplo, se conserva la relación:

\[
M(\texttt{CAN\_RUN}) +
M(\texttt{CPU\_RUN\_QUEUE}) +
M(\texttt{INACTIVE}) +
M(\texttt{INHIBITED}) +
M(\texttt{RUNNING}) = 1
\]

Esta expresión refleja que el hilo no se duplica ni desaparece dentro de la red: queda representado en uno de sus estados posibles. En la red de recursos, tanto en el modelo base como en el modelo consolidado de una CPU, se conserva la exclusión entre los modos globales de arranque y operación SMP:

\[
M(\texttt{PLACE\_SMP\_NOT\_READY}) +
M(\texttt{PLACE\_SMP\_READY}) = 1
\]

También se conserva el estado del recurso CPU:

\[
M(\texttt{PLACE\_CPU[i]}) +
M(\texttt{PLACE\_EXECUTING[i]}) +
M(\texttt{PLACE\_TOEXEC[i]}) = 1
\]

Este último invariante aparece en el submodelo reducido y en el modelo consolidado. Muestra que el token que representa al procesador puede estar en tres lugares: la CPU disponible, un hilo próximo a ejecutar o un hilo en ejecución. La transición \verb|TRAN_ADDTOQUEUE_FORCED| no cambia esa relación, porque su función es registrar un encolado obligatorio, no modificar directamente el estado de ejecución del recurso. Estos invariantes se calculan sobre la matriz de incidencia; por eso no dependen de los arcos inhibidores. Los inhibidores pueden habilitar o bloquear transiciones según el marcado, pero no agregan ni consumen tokens por sí mismos.\par

Los resultados \textit{bounded} y \textit{safe} deben leerse dentro del alcance del modelo. Las colas del planificador no se modelaron con una capacidad máxima fija, por lo que PIPE permite disparos repetidos de encolado y acumulación de tokens en plazas como \verb|PLACE_QUEUE| o \verb|PLACE_CANTQ|. Por este motivo, que la red no sea \textit{bounded} ni \textit{safe} no invalida la corrección analizada; simplemente indica que este modelo no impone una cota formal sobre el tamaño de las colas.\par

La matriz de incidencia del modelo consolidado confirma el punto central de la corrección. El encolado ordinario y el encolado forzado tienen el mismo efecto sobre \verb|PLACE_QUEUE| y \verb|PLACE_CANTQ|: ambos agregan un token a la cola per-CPU y un token a la plaza que penaliza futuras decisiones de encolado. La diferencia aparece en la matriz de inhibición. \verb|PLACE_CANTQ| bloquea el camino ordinario, pero no bloquea el camino forzado. Así, cuando FreeBSD necesita registrar un encolado obligatorio, la red puede actualizar su marcado sin quedar bloqueada por la política normal de balanceo.\par

La explicación de \textit{DTrace}, \textit{probes} y \verb|SDT| se desarrolla específicamente en el Apéndice \ref{appendix:dtrace-sdt}.\par
